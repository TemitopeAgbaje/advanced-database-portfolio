# Supalogi — Performance Analysis

## Test setup
- **Database:** PostgreSQL 15 on a MacBook
- **Data:** generated by `generate-data.sql`: 20,000 riders, 1,500 drivers,
  ~200,000 trips over 180 days, ~176,000 payments, ~211,000 ratings
- **Method:** `optimisation.sql` runs `EXPLAIN ANALYZE` on each query before and
  after an optimisation. `EXPLAIN ANALYZE` actually runs the query and reports the
  plan the database chose plus the real time taken.

## Results

Times are the "Execution Time" line from my run, saved in
[optimisation-output.txt](optimisation-output.txt). Times change a little on each run.

| Query | Optimisation | Plan before | Plan after | Before (ms) | After (ms) |
|---|---|---|---|---|---|
| Q1 Rider trip history | Composite index `(rider_id, requested_at DESC)` | Parallel Seq Scan | Bitmap Index Scan | 49.373 | 0.056 |
| Q2 Driver weekly earnings | Composite index `(driver_id, requested_at)` | Parallel Seq Scan | Bitmap Index Scan | 10.162 | 0.083 |
| Q3 Matching queue | Partial index `(city_id, requested_at) WHERE status = 'requested'` | Parallel Seq Scan | Bitmap Index Scan | 11.686 | 0.039 |
| Q5 Monthly city report | Materialized view `city_monthly_stats` | Seq Scan + Hash Aggregate | Seq Scan of 42 stored rows | 62.988 | 0.027 |
| Q4 Top 10 drivers | None (indexes ignored) | Parallel Seq Scan + Hash Join | Same | 42.886 | n/a |

## What I found

### Q1 and Q2: rider and driver lookups
Before the index, the database was checking through every row to find that rider ID.
It is like looking for a name in different records with no certainty of where it is,
so it takes longer. In my run it threw away about 100,000 rows per worker to find
just 5 trips (48 ms). After adding the index, it went straight to them (0.06 ms).
Q2 is the same idea for one driver's trips in the last 7 days.

### Q3: waiting trips (partial index)
The partial index only stores the waiting trips (`WHERE status = 'requested'`), so it
is easy to find them and faster to retrieve. It checks only the waiting trips, not
all 200,000.

### Q5: monthly report (materialized view)
An index cannot help here because the report cannot miss any record. It has to check
every trip. The materialized view saves the answer once, so the report only reads
42 rows (6 cities × 7 months) instead of 200,000. The catch is that the saved answer
gets out of date when new trips come in, so it needs refreshing every night with
`REFRESH MATERIALIZED VIEW city_monthly_stats;`.

### Q4: when the index is ignored
Q4 needs a lot of trips (about 30,000). When you need that many, reading straight
through the table is faster than using the index to jump to each one. So the database
was being smart when it ignored the indexes.

## The cost of indexes
Indexes are not free:

| Object | Size |
|---|---|
| `trips` table | ~19 MB |
| `idx_trips_rider_requested` | ~6 MB |
| `idx_trips_driver_requested` | ~6 MB |
| `idx_trips_waiting` (partial) | ~16 kB |

- **Space:** the two full indexes add ~60% on top of the table's size.
- **Write speed:** every new trip, and every status change, must also update each index.

So indexes were added only where a frequent, user-facing query needed them (Q1, Q2, Q3),
not on every column.

## Summary
| Technique | Used for | Why it fits |
|---|---|---|
| Composite index | Q1, Q2 | Frequent lookups of one rider/driver, filtered or sorted by time |
| Partial index | Q3 | Hot query over a tiny, constantly changing subset of rows |
| Materialized view | Q5 | Expensive report that is fine being a few hours old |
| No change | Q4 | Reads a large share of the table; full scan is already the best plan |
